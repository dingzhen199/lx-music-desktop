# 平台相似歌曲聚合推荐需求

日期：2026-09-20  
状态：待实现；供 subagent 执行。平台端点、登录要求、覆盖率及实际推荐效果尚未验证。

## 1. 目标与决策

将默认推荐流程改为：

**当前歌曲 → 各平台准确定位同曲 → 平台单曲相似推荐 → 跨源合并与排名融合 → 本地过滤和偏好调整 → 稍后播放队列。**

用户希望获得“从当前歌曲继续听”的推荐，不依赖文字模型凭歌曲名称推测声音，也不在本期自建音频模型或声学推荐系统。

本期产品默认值：

- 平台推荐为默认路径，不要求 AI Key。
- 默认路径自动触发的 LLM 请求数必须为 0，包括起点分析、候选排序和画像摘要生成。不能仅关闭排序，却继续后台生成摘要。
- 保留现有本地行为画像、去重、播放队列、自动续补和会话取消能力。
- 不保证聚合一定优于单平台；先验证数据可用，再比较聚合收益。
- 旧 AI 代码可以隔离保留，不要求新增双模式 UI；不得删除用户已保存的 AI 配置。若保留旧模式入口，必须明确区分，不能被平台推荐的失败降级自动触发。用户主动点击旧 AI 连接测试不属于自动推荐流程。

## 2. 当前事实与历史规格覆盖

当前 `recall.ts` 主要从同艺人搜索、LLM 生成关键词搜索、本地歌单召回。关闭 `ai.enable` 只会进入旧本地路径，并不会调用平台相似歌曲接口。

已知相关文档：

- `docs/recommend-similar-song-api.md`：早期接口接入草案，尚未实现。
- `docs/explore-radio/spec.md`：现有会话、电台、队列行为。
- `docs/user-profile/spec.md`：本地收藏、听完、跳过和画像。
- `docs/ai-recommendation-review.md`：近期缺陷修复与验证记录。

本需求覆盖以下旧设定：

1. 不再以 LLM 分析/排序作为默认推荐核心。
2. 不采用同艺人 `8`、歌单 `30`、搜索序号 `24 + 7*i` 等数值作为听感距离。
3. 不采用旧草案“为平台相似结果分配一个固定感知距离”的建议。
4. 平台全部失败时，不静默回退到关键词搜索、同艺人热门歌或旧 AI 排序并宣称是平台相似推荐。
5. 允许修改 `engine.ts`、`prompts.ts`、`judgment.ts` 等相关模块；旧文档的阶段性只读约束不阻止本次必要改动。

## 3. 实施阶段

### P0：平台能力核实

优先调查网易 `wy`、QQ `tx`，这是调查顺序，不是已确认可用的平台列表。

交付一份实际调查记录，至少包含：

- 平台、验证日期、端点/调用方式、请求字段和真实响应结构。
- 是否需要登录、可在项目当前认证条件下使用到什么程度。
- 是否确实为“按单曲返回相似歌曲”，而不是热门歌曲、推荐歌单或普通搜索。
- 种子歌曲标识与返回曲目标识如何转换为项目的 `MusicInfo`。
- 返回顺序/分数含义、分页或候选上限、已观察到的限流及错误表现。
- 脱敏响应样例；不得把登录凭证、Cookie、Key 写入文档、fixture 或日志。

**不得依据接口名称、旧文档或记忆臆造端点和字段。** 当前只有搜索能力的音源，不得冒充相似歌曲提供方。

先核实能否获取真实结果，再实现对应适配器。若某平台不可用，记录原因并继续核实其他目标平台；需要用户提供登录条件时明确列出缺失项。所有目标平台都不可用时，应交付调查结果和阻塞原因，不以 mock 或普通搜索冒充接入完成。

### P1：单平台完整闭环

至少一个经过 P0 验证的平台完成：种子定位、真实相似召回、过滤、显示、入队、切歌、续补、错误处理。

这一阶段用于验证候选质量和播放器集成。仅完成一个平台时必须报告“单平台完成”，不能报告“多平台聚合完成”。

### P2：多平台聚合

接入第二个经过真实验证的平台，完成跨源身份合并、来源保留、排名融合和单源故障降级；比较单平台与聚合结果。

实现过程按 P0 → P1 → P2 推进，不要求一次支持所有音源。

## 4. 功能要求

### 4.1 起点定位

- 优先使用当前歌曲已有的原生平台标识。
- 在其他平台搜索同曲时，核对歌名、歌手、版本信息，并在有数据时辅助核对专辑、时长。
- 原唱/翻唱、录音室/现场、伴奏/人声版本不能仅因清洗后歌名相同就被认为匹配成功。
- 元数据缺失不算匹配证据。找不到可靠匹配的平台跳过，不取搜索第一条充数。
- 区分“确认是同一录音/版本”的匹配与“推荐结果中避免同一作品重复”的去重，不把宽松去重函数直接当成跨平台种子匹配规则。
- 当前 `SessionAnchor` 主要保存 `id/artist/title`，可能不足以定位原平台歌曲；应沿会话传递必要的 `source` 和原生歌曲标识，不依赖解析一个全局 id 字符串猜测平台字段。
- 本地文件或下载条目可用元数据做跨平台匹配；没有可靠匹配时展示无匹配结果。

### 4.2 平台适配器

提供统一的相似歌曲调用边界，具体类型由实现者按项目风格确定，至少表达：

- 提供方、该提供方的种子歌曲标识。
- 结果列表、平台原始排名、候选音乐信息。
- 分页/是否还有候选（仅在接口真实支持时提供）。
- `成功 / 无匹配 / 空结果 / 需要登录 / 限流 / 请求失败 / 已取消` 等可区分状态。

要求：

- 每个平台独立失败，不能通过一个异常使其他平台成功结果全部丢失。
- 复用项目现有网络和 SDK 设施，设置有限超时、并发和重试；不无限重试。
- 请求级重试只在一个层次执行；单源部分成功、限流与会话重试不要叠加放大流量。
- 不为每首候选立即探测所有播放 URL。区分“具有可交给播放器的音乐标识”和“已验证当前可播放”，实际播放继续使用既有音源解析/切源能力。

### 4.3 合并与排序

候选内部至少保留：作品/版本身份、一个或多个音源条目、推荐来源及各来源排名。不能提前用“保留第一条”的去重把其他来源证据丢掉。

默认融合策略：

- 优先使用来源内排名，避免不同平台原始分数不可比的问题。
- 可采用等权倒数排名融合 `Σ 1 / (k + rank)`；`rank` 从 1 开始，`k` 为集中配置的正数。该公式仅为初始排序方案，不代表声学距离或经过证明的偏好概率。
- 同一平台对同一候选最多贡献一次；重复行、重复页面、重试返回不能变成多次“投票”。
- 多源共同推荐可以加分，但不能只按来源数量决定顺序；保留单源高排名候选获得展示的机会。
- 相同输入必须产生确定性结果；异步返回先后不能决定最终排名。
- 接入现有本地画像作为有界的次级调整，保留来源排名的主要作用；不得调用 LLM 摘要，也不得让单次跳过变成永久封禁一个艺人。
- 保留艺人多样性限制；不足一批可以返回少量结果，不从无关来源补足数量。

播放来源选择与推荐分数分开：推荐方不一定是最终播放源。跨源合并后保留备用音源信息，避免去重后只剩一个不可用条目。

### 4.4 过滤规则

继续排除：

- 起点自身及不应重复出现的同曲变体。
- 当前会话已推荐、已消费的曲目，含跨平台同曲。
- 已在稍后播放队列中的同曲，避免推荐重复插入用户手动排队的内容。
- 明确“不再推荐”的曲目。
- 当前设计中被排除的“我喜欢”歌曲，保持现有发现新歌语义；不在本期擅自改成优先重复播放收藏。

语言、纯音乐、风格等条件只能基于可靠元数据执行。没有证据时保留 unknown，不能由歌名或 LLM 自报补造属性。若提供严格属性筛选，未知项不得显示为“已满足”。

### 4.5 会话与续补

复用并保持：

- 推荐追加队尾，不打断当前歌曲。
- 当前请求只属于发起时的会话代际；关台、换起点后迟到结果不能入队。
- 用户连续切歌有防抖，在途续补单飞；取消后不继续发起后续平台请求或重试。可取消的在途网络请求应使用现有取消能力。
- 移除推荐队列项时仅操作本会话实际插入的项，不误删用户手动加入的同 id/同曲条目。
- 路径点击播放只消费目标一次，不能清空其余稍后播放队列。
- 关闭电台停止续补，保持已有的清场语义。

续补应先消费已缓存但未入队的候选，再按真实分页能力获取更多。**同一锚点的有限结果消费完是“候选用尽”，不是网络失败**：不计为请求错误、不反复重试相同结果、不静默切回旧推荐。

本期不默认对候选递归调用“相似歌曲”进行多跳扩张。候选用尽时提示用户切换起点或刷新；没有刷新能力的平台不能承诺刷新一定产生新歌。

### 4.6 缓存

- 缓存按平台、种子原生标识和必要的账号上下文区分，设置明确 TTL 与容量上限。
- 缓存原始归一化结果；当前会话的排除、偏好和队列过滤应在读缓存后重新执行。
- 失败/限流不得写成长期有效的“成功空列表”；会话已取消的调用也不得伪装成失败。
- 多次续补避免重复请求同一平台、同一种子和同一页。
- 保存缓存不包含认证信息或短期播放 URL。

### 4.7 页面与设置

- 对用户显示“平台推荐/聚合推荐”和真实推荐来源，不再标为“AI 计划”。
- 理由使用可验证事实，如“网易相似歌曲推荐”“两个平台共同推荐”；不能生成“节奏高度一致”等未经测量的描述。
- 隐藏或移除平台模式下没有真实含义的听感距离滑杆、弧线角色标签和自由文本听感指令；不得把融合排名重新包装成 0–100 听感距离。
- 反馈使用明确可执行语义。推荐默认：“喜欢这首”“不再推荐这首”；与加入收藏区分，不隐式修改收藏列表。
- 原有 `good/far` 若需迁移，不再依靠修改旧 radius 生效；新的反馈语义、对应本地信号应在实现说明中写清楚。
- 单源失败、有其他结果：继续展示推荐，并以非阻断方式提示部分来源不可用。
- 全部请求失败、没有同曲匹配、结果被过滤完、候选已用尽应有不同状态。
- 设置页推荐功能不再表现为依赖 AI 开关或 Key。旧配置可兼容保留，但不能误导用户以为开启 AI 是平台推荐的前提。
- 同步四种现有语言资源，不留下缺失 key。

## 5. 非目标

- 自建或接入音频大模型、音频向量库、BPM/音色分析、批量候选音频下载。
- 依赖文字模型知识生成候选、判断候选声音、撰写听感理由。
- 建立多用户协同过滤服务，上传本地用户画像。
- 覆盖所有音源；提供未经验证的平台端点。
- 重写播放器、升级 Electron/基础框架，或清理本次无关代码。

## 7. 验收标准

| 编号 | 要求 |
| --- | --- |
| AC1 | P0 有真实接口验证与脱敏样例，明确每个平台的能力、认证条件及失败表现 |
| AC2 | P1 至少一个真实平台完整闭环；P2 至少两个真实平台完成聚合。只有 mock/适配器骨架不算完成 |
| AC3 | 无 AI Key 可推荐；即使旧 `ai.enable=true`，平台模式推荐、续补、反馈及累计满画像摘要阈值均不发 LLM 请求 |
| AC4 | 跨平台错版本、同名不同歌、缺失歌手等歧义有测试；不能错误映射种子或强行取搜索第一名 |
| AC5 | 合并后保留各来源排名和备用音源；同源重复不重复计分；输入完成顺序变化不改变结果 |
| AC6 | 起点、已推荐、当前队列、收藏排除及明确不喜欢的歌曲不重复入队；多样性和画像调整有测试 |
| AC7 | 单源超时/异常不丢其他源结果；全部失败、无匹配、空结果和候选用尽可区分，无无限重试 |
| AC8 | 请求中关台/切换起点后旧结果不入队；路径播放不清队列，清场不删除用户手动项 |
| AC9 | 缓存 TTL、容量、同源同页去重、偏好变化后的重新过滤和取消处理有覆盖 |
| AC10 | 页面无伪声学距离、无编造听感理由、无默认 AI 依赖；四语言和旧配置读取正常 |
| AC11 | 相关自动化测试、全量 Vitest、ESLint、主/渲染进程 TypeScript 检查和生产构建通过 |
| AC12 | 有真实单平台/聚合冒烟记录；明确未验证事项，不把技术通过等同于听感效果已证明 |

建议验证命令：

```sh
npm test
npm run lint
npx tsc --noEmit -p src/main/tsconfig.json
npx tsc --noEmit -p src/renderer/tsconfig.json
npm run build
```

真实效果小样本记录：选约 20 首覆盖不同艺人、语言、热门/冷门及版本的起点，比较单平台与聚合的前几首；记录同曲匹配成功率、有效候选数、重复/同艺人集中程度、耗时，以及人工是否愿意接着听。样本用于发现问题，不宣称统计上证明聚合更好。若缺少用户试听，仅报告客观结果与待试听清单。
