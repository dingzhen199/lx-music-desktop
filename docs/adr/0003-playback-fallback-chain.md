# 播放失败回退链：提供方外层、音源内层；自动换源写回「我的列表」

**Status**: accepted（2026-09-21，两轮 grill-with-docs 裁决 Round 1 Q1–Q10、Round 2 Q1–Q9）

播放取流失败时的自动回退按**提供方外层、音源内层**编排：`tx@主源 → tx@备源1 → … → tx@备源n → wy@主源 → wy@备源1 → …`，候选提供方来自 findMusic 同曲匹配（按音质丰富度排序），每个提供方只试一档音质（该平台可用音质中的最优档，即 getPlayQuality 现状），失败即切音源、不做同平台降档重试。排序理由是语义而非成本：**音源只是取流载体，换提供方才是换歌曲版本**，用户对原提供方的版本有偏好，换版本应是更靠后的一级。（成本论在评审中被质疑后撤回：findMusic 是 4-5 个并行搜索请求且有按歌缓存，墙钟时间不构成排序依据。）

自动换源成功后，仅**提供方变更**写回「我的列表」（复用手动「歌曲换源」机制，随列表多端同步）；成功的音源不写入歌曲——音源是全局状态而非歌曲属性；排行榜、搜索结果、电台队列等临时上下文只在本次播放生效。备源仅服务播放取流：搜索、歌词、封面仍走主源（歌词/封面维持既有跨提供方回退）。触发层限于取流失败层；音频加载错误路径维持「刷新 URL ×2 → autoSkipOnError」，但每次刷新重走取流链，间接受益于音源轮换。

同曲匹配规则不变：归一化歌名 + 歌手三轮匹配 + 版本标记一致 + 时长 ±5 秒，findMusic 一套规则供自动/手动共用。自动换源对探索电台视为**同曲**：不触发跟歌重锚，路径与去重照旧。

## Considered Options

- **提供方外层、音源内层（采纳）** vs 音源外层、提供方内层（否决：把"换版本"放在"换载体"之前，违背版本偏好优先）。
- **换源写回「我的列表」（采纳，用户裁决）** vs 仅会话内记忆（否决：同一首歌每次播放都要重走整条失败链）vs 连成功音源也写入歌曲（否决：歌曲模型无此字段，属为优化埋数据）。
- **保留布尔同曲规则（采纳）** vs 引入"歌名 + 节奏相似度 ≥80%"阈值（否决：时长相似度 80% 对 4 分钟的歌意味着 ±48 秒，比现有 ±5 秒松十倍，串烧/加长/电台版会错配；文本相似度已被归一化 + 版本标记覆盖；真节奏分析需先取流下载音频，与失败环节循环依赖）。
- **版本标记一致（采纳）** vs 版本变体（Live/DJ/伴奏）作最后一级兜底（否决：换错版本比跳歌更伤，违背同曲语义；可作后续增量）。
- **备源仅服务播放取流（采纳）** vs 全部 API 调用轮换（否决：动机是播放失败，搜索/歌词/封面已有各自回退，改动面失控）。
- **不加新设置、回退常开（采纳）** vs 新增开关（否决：回退是纯韧性能力，终态已由 player.autoSkipOnError 控制）。

## Consequences

- 多活音源要求 `userApi.apis` 与全局 `qualityList` 从单份改为按源一份，`getPlayQuality` / `assertApiSupport` 相应按源取值；「自定义源管理」页新增勾选启用 + 拖拽排序，第一个启用的为主源。
- 429 限流从「随机等 2-6 秒重试同源」改为「立即切下一个源」；不做失败源记忆或降权。
- 回退链整体受现有 100 秒取流超时兜底；全部穷尽后沿用 autoSkipOnError 终态（开 → 5 秒后下一首，关 → 停在错误状态）。
- 换源过程反馈沿用状态栏文字（补"切换音源"文案），不新增 toast。
- 写回的提供方变更随「我的列表」同步传播到其他设备，与手动换源行为一致。
