# 探索电台：跟歌重锚、run 级策略与分析作废

**Status**: accepted（2026-09-12，三轮 grill-with-docs 裁决）

推荐功能从"手动起点的单歌会话"演进为**探索电台**：电台开启期间，用户切到路径之外的歌曲即立即清场并以新歌为锚点重新开台，不设播放时长提交阈值；推荐一律追加稍后播放队尾；探索距离、一句话约束、far/good 反馈以"run"（一次开播到收台）为作用边界跨锚点沿用，收台即清；一句话约束一旦变化即作废锚点分析，下一次计划重新解读锚点。收台触发集仅两项：显式关闭电台、同一 run 内连续三次计划最终失败（初始与续补均计入，任一成功即清零）；切歌伴随的队列清空一律以重锚为准而非收台，独立的"清空稍后播放"触发在用户界面出现独立手势前不实现。电台开关为持久设置：重启后仍为开时，首次播放事件即自动以当前歌开台。

成本立场：**不设任何额度闸**。跟歌模式下连播自己曲库时每一首都触发一整套"锚点分析 + 分批排序"LLM 调用，这是用户明确接受并自担的代价，换取行为可预期（切歌即新台）；无 API Key 时电台照常开台，全程走本地引擎。

## Considered Options

- **跟歌重锚（采纳）** vs 30 秒提交阈值（否决：多一层"何时算数"的心智负担）vs 站点电台（偏离即停、不显式重开，否决：与"电台化"目标矛盾）。
- **run 级策略沿用（采纳）** vs 每台重置（否决：换歌就失忆）vs 设置级持久口味档案（否决：违反"此刻状态优先"，不无限拟合过去）。
- **约束变更即作废锚点分析（采纳）** vs 仅硬约束才重分析（否决：判定分级引入第二套规则，用户选择成本换取召回源头正确）。
- **不设额度闸（采纳）** vs run 级软上限（否决：自用场景，成本自担）。
- **只做探索弧线语义（采纳）** vs 另做"相似歌曲列表"模式（否决：单一引擎，相似只是低距离的探索）。

## Consequences

- 电台无遥测、无口味持久化，质量信号只有本地产出的四个自用计数器（30 秒跳过率、far/good 比、run 存活、续补消费比）。
- 模型对冷僻候选的"想象式打分"由全半径低置信拦截兜底（不再只是近距离拦截）。
- 手动起点会话既有的幂等语义保留，只是触发方从手动点击扩展为切歌事件。
- 切歌风暴仅靠重锚计划的防抖（与续补同量级，约 1.2 秒）吸抖；epoch 代际仍负责在途计划的错序防护。
- 指标的时长判定依据为实际播放秒数（play/pause 事件累计），不取切歌墙钟间隙，避免暂停被计入。
