# AI 歌曲推荐审查与修复（2026-09-20）

审查范围：当前工作区的推荐引擎、跨源召回、LLM 请求与输出解析、会话/播放队列、音频特征与用户画像。保留审查开始时已有的未提交改动，在其上修复。

## 设计判断

整体分层合理：音乐平台提供真实候选，模型分析起点并判断候选，确定性规则过滤，最后由会话编排提交播放队列。这样能避免让模型凭空生成不存在的播放链接。纯函数和运行时适配器分离，也便于测试。

重点问题在模块之间的语义不一致：请求失败与候选不合格混用同一回退路径、人声连续性被当成是否有人声、异步结果错误归属到更新后的状态。本次修复集中于这些边界。

## 已修复

| 问题 | 可复现的影响 | 修复 |
| --- | --- | --- |
| AI 淘汰被本地回退绕过 | 全部候选 confidence=low 时，仍会从原候选池本地排序并入队 | 仅请求失败的批次允许本地回退；有效空 ranking 不重试、不复活；其他批次的 AI 成功结果照常保留 |
| 输出校验接受隐式数值转换 | 空串/布尔值候选编号映射到第 0 首；越界编号不触发重试；null 距离当成 0 | 校验批内整数编号，无有效编号的响应重试；缺失距离按距离标签处理；缺失连续性不当作零 |
| 器乐硬约束互相冲突 | 选完前 8 首再过滤会漏掉其余器乐；低人声相似度误放行人声曲；近距离又误杀明确要求的器乐 | 过滤提前到选曲前；提示词增加独立 vocal_type；用户要求器乐时豁免人声转换，但保留其他守门；“不要人声”不再因子串匹配误杀“无人声” |
| 起点特征错配 | 播放下一首后修改约束，重新分析旧起点时却把当前曲的音频特征和进度传给模型 | 采样前后检查起点身份；起点不在播放时使用无有效音频特征的元数据分析，不冒用其他歌曲的数据 |
| 采集器启动/停止竞态 | 动态加载播放器期间停止或重启，旧 start 仍安装定时器和事件监听器 | 按代际限制资源安装；旧启动流程无法覆盖新流程，stop 可以完整清理 |
| 画像摘要吞掉在途增量 | 请求覆盖 20 个事件，期间又新增 20 个，返回时却标记已覆盖 40 个 | basedOnCount 取请求快照；成功后积累够阈值则继续生成，失败仍保留旧摘要且不自动死循环 |
| 跳过误用前曲时长 | 短曲之后的下一首没加载到元数据，20 秒跳过会被误判为已听完而漏记 | 时长快照绑定曲目身份；已知短曲的 complete/skip 互斥保持 |

本记录更新早期 Spec 的两处实现约束：器乐一致性修复需要调整 `judgment.ts` 与 `prompts.ts`；运行时编排现已能通过 mock IPC、播放器与事件边界进行 Vitest 测试。画像摘要仍通过独立 `profileSummary` 通道进入排序提示词，不进入用户约束解析。

## 验证

- 新增引擎边界、画像异步和采集器生命周期回归用例，并更新器乐语义测试；多项用例先在修复前复现失败，再验证修复。
- 全量 Vitest：27 个测试文件、494 个测试通过（审查开始时为 471 个）。
- ESLint、主进程/渲染进程 TypeScript 检查、生产构建通过。
- 未调用真实模型或真实音乐源做端到端试听；测试验证逻辑与构建，不代表推荐听感已经验证。

## 仍需认识到的设计限制

- 音频特征是粗略信号统计，候选没有对应音频特征；跨歌曲听感判断主要依赖模型先验。显式器乐类型和低置信过滤只能减少误判。
- 本地候选距离来自召回来源与查询顺序，不能视作实际听感距离。本地模式的匹配能力会弱于模型排序。
- 会话取消会丢弃过期结果、停止后续步骤和重试，但已经发出的 HTTP 请求不会立即中止，快速切歌仍可能占用并发与额度。现有文档明确接受无额度闸，本次没有额外改变该策略。
- 推荐质量还需固定曲集试听：人声/器乐转换、中文/日文/韩文约束、冷门歌曲、极近/极远半径，以及连续播放多个批次。
